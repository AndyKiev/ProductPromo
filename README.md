# ProductPromo

Back-office for product cards & promotions — FastAPI + React/TanStack, talent-app
conventions, running against a **native host PostgreSQL** (legacy column names,
no schema changes — the driver is parametrized, MySQL still works).

This is a **working slim scaffold**: it boots and serves the **Nomenclature** CRUD
(market → segment → category → family, plus keys and the market/segment/category/family
join) against your MySQL. Auth is a dev stub and the DB-backed i18n is a documented
port — both called out below.

## The database is not a container

It is a **native Windows PostgreSQL 18 cluster on the host** —
`C:\Users\andre\PostgresData\product_promo`, `127.0.0.1:5435`, db/user
`product_promo`/`admin` — so no `docker` command can destroy it, and it matches
production, where the DB is an external server. It is **not** a Windows service,
so it does not start at boot.

Read [docs/DB_MIGRATION.md](docs/DB_MIGRATION.md) before touching any of this.

## Quick start — Docker
```bash
make db-up                          # start the host Postgres FIRST (every boot)
cp stack.env.example stack.env      # already filled in for the host cluster
make docker-up                      # build + start backend and frontend
```
- Frontend → <http://127.0.0.1:8013>  (login `UKR7101004` / `111`)
- Backend / Swagger → <http://127.0.0.1:8012/docs>

Host ports are 8012/8013 because talent (8005) and anee_data (8006, 5173) are
already running; inside the containers the apps still listen on 8004 and 8009.
There is no nginx service — the SPA calls the published backend port directly.

## Quick start — local (no docker)
```bash
make db-up                           # the same host Postgres
cd backend && cp .env.example .env   # already points at 127.0.0.1:5435
make -C .. install-backend && make -C .. run-backend     # :8004
# frontend (separate terminal)
cd frontend && cp .env.example .env
make -C .. install-frontend && make -C .. run-frontend   # :8009 (calls :8004)
```

## Before it's "real" — two deliberate stubs
1. **Auth is a dev stub.** `backend/backend/auth/jwt_auth.py` accepts any login and
   returns a fixed employee so the SPA works. Port the talent LDAP-bind + RS256 JWT
   (keys via `generate_keys.sh`) into `get_current_active_auth_user`. See
   `backend/backend/auth/README.md`.
2. **i18n is fallback-only.** `BaseService` returns each domain message's English
   `fallback`. The DB-backed translation (msg / msg_key by employee language) is a
   port from talent; wire it into `_resolve_domain_error/_success`. The ukr/eng
   **name** resolution for reference rows already works via `base/i18n.py:lang_suffix_for`
   — point it at the real employee language field once auth is wired.

## Notes
- **No DB schema changes.** Models map physical legacy column names via
  `mapped_column("RealName", ...)`. There is no alembic — tables are created by
  `Base.metadata.create_all()` (`backend/backend/database/init_db.py:bootstrap`,
  run from the entrypoint and by `make init-db`).
- **Driver is parametrized.** `APP_CONFIG__DB__DRIVER` switches between
  `postgresql+asyncpg` (the default, and what this now runs on) and
  `mysql+aiomysql` (+ `cryptography` for MySQL 8 auth).
- **Redis** isn't required by this slice and is omitted; add a service + the `redis`
  dep when you need caching/celery.
- The TanStack route tree (`frontend/src/routeTree.gen.ts`) is generated by the vite
  plugin on first `npm run dev` (gitignored).
